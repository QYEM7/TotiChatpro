- **العملة:** البيع عن طريق وكلاء الشحن خارج التطبيق، ولا عمليات شراء IAP داخل التطبيق حسب المواصفة الحالية؛ أي أرقام نقد في CI وهمية للاختبار وليست مدفوعات فعلية.
- **الوكالات:** فصل وكالات المضيفين عن وكلاء الشحن. إدارة وكالات المضيفين الكاملة للمالك وشريكه الرئيسي المعيّن فقط؛ الرتب المسماة Super Admin الأخرى ليست بالضرورة صاحبة صلاحيات الشريك. موظف DB لا يفتح وكالات شحن؛ أي دور تفويض لفتح وكالة مضيفين يحتاج مساراً مستقلاً منضبطاً.
- **انتقال المضيف:** الأصل موافقة الوكيل القديم. إذا حصل رفض تعسفي/تجاهل/تعطل الوكالة يوجد مسار شكوى وتحقيق استثنائي للإدارة؛ لا نقل تلقائي بمجرد اختيار الوكالة الجديدة.
- **الماس ونهاية الشهر:** قيد 30% عند فك الماس للعملات، حفظ الحسابات النهائية وسجلات المستحقات والتارجت والرواتب أولاً، ثم فقط تصفير رصيد الماس التشغيلي حتى لو لم يُفكَّ يدوياً؛ لا إعدام حق مالي مستحق أو استبدال قرار مالي لم يعتمد.
- **الهدايا:** اختيار المستلم والهدية قبل زر إرسال مستقل، وتأثيرات الهدايا تظل جزءاً من هوية الغرفة.
- **الألعاب:** ألعاب فردية وجماعية داخل الغرفة دون قطع الصوت أو إزالة المقعد/المايك.
- **الصوت والموسيقى:** لا اعتبار للمقعد المحجوز أنه اتصال صوتي ناجح؛ يجب LiveKit/TURN واتصال مسموع بين جهازين. قوائم الموسيقى تحفظ للمستخدم والتشغيل يسمعه الجميع بصورة متزامنة وبمحتوى مرخّص.
- **النسخ الاحتياطي:** استرجاع PostgreSQL المحلي وStorage المحلي نجح فقط على ملفات/أرصدة وهمية؛ **ليس** نسخة إنتاج. باقة Supabase Free لا تُغني عن نسخة إنتاج مستقلة موثوقة ونسخة بايتات Storage منفصلة.
- **الآمان:** مستشار Supabase أعطى 24 إشعار `INFO rls_enabled_no_policy`، لا تُعتبر جميعها ثغرات بحد ذاتها؛ وبعض الجداول مغلقة قصداً. وكذلك 5 FK indexes ناقصة بالإنتاج وهناك Migration متوقفة للتغطية و35 `INFO unused_index`. لا فتح صلاحيات عامة لإسكات فحص.
- **GitHub:** القواعد/حماية الفروع تحتاج توثيق وتفعيل Admin؛ واجهة GitHub API أرجعت قيود صلاحية عند محاولة قراءة Branch Protection، وRulesets الظاهرة 0.
- **الإصدار:** بوابة T48 لا تسمح ببناء APK بسبب `release_allowed=false`. تشترط **التطوير ≥80% والجاهزية Beta ≥80% كلتيهما**، 40/50 مهمّة بحالة `verified_live`، إثبات استرجاع قاعدة وStorage، Staging مستقل، اختبار هاتفين، صوت وتدقيق مالي، مراجع وتاريخ موافقة وقرار Owner. 80/80 **شرط لازم وليس كافياً**.

## تسلسل التنفيذ الإلزامي للأعمال P0
1. **أولاً T49/T03/T07:** نسخة مشفّرة من الإنتاج واختبار استرجاع مستقل يشمل ملفات Storage، إذن تكلفة Staging، حماية فروع GitHub. لا تدفع ولا تنشر دون موافقة.
2. **بعدها T01/T04/T05/T38/T39:** تطبيق 10 migrations على Staging فقط ثم اختبار الصلاحيات وعزل المستخدمين والوكالات والتحقق بالواقع.
3. **بعدها T12/T13/T15/T16/T17:** SMTP/OAuth الحقيقي وحسابات فعلية وغرف/حضور واتصالات إعادة الدخول.
4. **بعدها T20/T21/T18/T19/T22/T23:** تهيئة LiveKit/TURN واختبار صوت وموسيقى بين هاتفين مع بقاء المقاعد والمايك.
5. **بالتوازي T24/T25/T29/T30/T33/T34/T35/T36:** محاسبة المال الفعلي وأدلة الوكلاء، اعتماد معدلات الرواتب، تجربة التسوية الشهرية التي لا تضيع حقوقاً.
6. **ثم T09/T10/T11/T26/T27/T32/T37/T40/T41/T42/T43/T44/T45/T46:** إكمال جميع الأزرار والواجهات والألعاب والتقارير والجودة والأمان.
7. **أخيراً T47/T48/T50:** اختبار جهازين وأمن مستقل ومراجعة 40/50 حالة live وأدلة الإصدار، ثم فقط بتصريح Owner بناء نسخة موقعة وتنفيذ تجربة 30 يوماً ورصدها.
