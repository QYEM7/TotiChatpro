# TotiChat Voice Token Bridge (development)
Date: 2026-10-10.

Old project `bfadhdnudmsggylunhlh` provides a reference `livekit-room` Edge Function using LiveKit server SDK and JWT. Its old members, session IDs and keys were not imported.

New project `sqedsnyvjblvbjbizcay` now has `phase2-voice-token`, with JWT verification enabled. It reads the user's real Supabase identity and room membership through authenticated RLS, then issues a short-lived LiveKit participant token. Publishing permission is granted only to the real seat holder with microphone state unmuted; non-seat users can subscribe only. A missing external LiveKit URL/API key/secret fails with an explicit HTTP 503, not simulated audio.

Migration `phase2_actual_mic_mute` controls changing the user's own mute state through a signed-in RPC. Users cannot unmute without a reserved seat; guest clients cannot call the function.

## Integration update

The **actual** LiveKit browser client is now locally bundled into the Android
WebView from `app/phase2-livekit-sdk.mjs` using esbuild, without a CDN or
untrusted external JavaScript. `app/phase2-voice-ui.js` displays explicit
Connect Audio and Seat Microphone buttons for authenticated room members,
obtains short-lived server-signed tokens and sends audio tracks only when
the user has a valid mic seat. Room exit and seat changes disconnect the
client's microphone transport. No signal is fabricated.

The Android manifest generated by Capacitor now declares both
`RECORD_AUDIO` and `MODIFY_AUDIO_SETTINGS`. Capacitor
`BridgeWebChromeClient` handles WebView permission requests; real Android
microphone prompt behavior must still be tested on physical devices.

The missing **LiveKit backend secrets** still prevent actual audio. The
server correctly rejects requests with a `LIVEKIT_NOT_CONFIGURED` error
until LiveKit infrastructure exists; this is not a bug that can be fixed by
adding fake tracks.

**Security gate before public beta:** invalidation/revocation of SFU
publish permissions after server-side seat state changes (e.g. admin
modifies another user or an old token remains connected) needs a
server-to-LiveKit permission update/reconciliation strategy and abuse tests,
not merely a cooperative client disconnect. Existing client disconnect
prevents normal-user stale mic publication but does not prevent a malicious
client; do not certify microphone moderation as complete.

Check status via GitHub Actions, then test on two actual Android phones
with LiveKit configured before public month-long beta.
